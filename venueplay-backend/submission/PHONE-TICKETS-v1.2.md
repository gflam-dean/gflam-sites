# The bingo ticket on a phone: what OLGR will want, and what VenuePlay does now (v1.2)

Version 1.2, 27 October 2026. Supersedes `~/venue-enrich/rng-certification/qld/PHONE-TICKETS.md` (16 October 2026, read from commit 559dbe00), whose sections 3 to 5 described tickets made on the host's tablet and claims judged in the console, and recommended moving both to the server. That recommendation was carried out on 19 October 2026 (VP-DRAW-1.0, migration 104) and the live product has run that way since. This version keeps the regulator's thirteen questions (section 2 of the old file, unchanged in substance) and gives the answers as the code stands at commit 18e2c58d, live on 27 October 2026. Line numbers are to that commit; "S" is `venueplay-backend/worker/vp-draw.js`, "T" is `venueplay/app/vp-draw.js`.

OLGR's 18 August 2026 letter called these "Portable Electronic Tickets" and said the app software should be submitted to the Technical Unit. No Queensland standard for them exists (QLD-PATH.md section (d)); the tests will be the Act's own words and the general integrity test in s 100(2)(a).

## 1. One path now

There used to be two bingo paths (a live tablet path and a built server path). There is one. The host opens `/app` (the console, `venueplay/app/index.html`), which loads the regulated module `/app/vp-draw.js` and refuses to deal, draw or judge anything if that script did not load (index.html line 3095). The console asks the game Worker for the draw at game start, for every ball, for every phone's tickets and for the verdict on every claim. The tablet stands in only when the server cannot be reached, only where the state's switch allows, and everything it does then is written to the server's record as soon as it can be, labelled as the tablet's (RNG-DOSSIER-v1.2.md sections 5.3 and 5.5).

## 2. What OLGR will want to see

The thirteen points from the 16 October file, unchanged: 1 ticket generation; 2 allotment; 3 immutability; 4 display fidelity; 5 marking; 6 win verification; 7 identity and anti-forgery; 8 duplication and replay; 9 records; 10 no selling on the phone; 11 software integrity; 12 failure behaviour; 13 separation of patron data (Submission Requirements 6.17).

## 3. How VenuePlay does it now

1. **Generation.** On the server: `generateStrip()` (S 500 to 506) builds a strip of six tickets covering 1 to 90 exactly once with the shared VP-STRIP-1 block (S 399 to 499) and `randInt` (VP-SCALE-1), and validates every strip before returning it. A player's ticket k is page k mod 6 of book floor(k / 6), so tickets bought one at a time come from the same strip; undealt pages are stored with `dealt_at` null and never sent before they are dealt (migration 104). On the tablet, only during a recorded outage before the first ball: `makeStrip()` (T 133 to 137), the same block with `cryptoInt`. Every ticket is a valid housie ticket by construction and by `ticketIsValid` (S 451 to 465).
2. **Allotment.** The console asks `POST /host/bingo/deal` with one hand per phone: the phone's pid (its signed key fingerprint), its server device id, and the count wanted (S 619 to 660). The count is the host's default on a free night or the units the bar sold on a paid night, capped at 24 (`BINGO_DEAL_MAX_TICKETS`, S 394). The server writes each ticket to `vp_bingo_tickets` with the draw, pid, device id, book, page, cells, ticket number, `dealt_at`, `source` (`server` or `tablet`) and `balls_at_deal`, the number of balls standing when it was dealt (S 752 to 766). A count corrected down voids the newest tickets; the rows stay (S 768 to 771).
3. **Immutability.** The phone never sends a ticket. A claim carries only the ticket number (`pressBingo`, `play.html` 1457). The server judges on its own copy (S 867: "this server's copy, never anything the phone or the tablet says is on it"). A tablet ticket counts only if it was on the record before any ball (S 865 to 869). A player altering the phone's page or storage changes nothing the server checks.
4. **Display.** The phone renders each ticket from the cells it received, with its ticket number, and recognises a re-sent identical set so a winner's screen is not reset (`play.html` `cards` handler from 1562). The phone shows the numbers called. **Not played on a screen for this document** (no browser in this pass); the 26 October check saw the code paths and not the paint (lodgement checklist B3).
5. **Marking.** Daubs are local and cosmetic; the phone's own BINGO gate and the server's verdict are computed from the called set only.
6. **Verification.** `POST /host/bingo/claim` (S 794 to 902): the server reads its own tickets for that pid, its own standing balls in order, takes the first `balls` of them (the number out when the player pressed), and applies `bingoTicketWins` (S 529 to 557) for the pattern named, or `customTicketWins` (S 585 to 596) with the venue's saved rule read from the venue's own row (S 600 to 606). It writes one `vp_bingo_claims` row whether or not it is a win: ticket, pattern, ball count, last ball, verdict, winning cells, where it was decided, and for a custom pattern the pattern id and a copy of its name and rule. The host confirms or rejects through `/host/bingo/claim/resolve` (S 945 to 963); a host cannot confirm a claim the server judged a non-win (`bingoMayConfirm`, S 907 to 911), except a claim decided on the tablet during an outage the server itself recorded, and only where the state's switch allows. A claim sent again returns the first verdict (S 810 to 812). The console's list of called numbers is compared, not used.
7. **Identity.** `vp-phonekey.js` (unchanged since 17 October, hash `39dc4931...`): each phone mints an ECDSA P-256 keypair per room, its pid is `k1_` plus the SHA-256 of the public key, and every join, claim and leave carries the public key, a counter and a signature over every field the console acts on. The console verifies the key hashes to the pid and the signature verifies, and refuses an unsigned message about a keyed pid. Unsigned legacy phones were switched off on 25 September 2026. **Gap, stated plainly:** the server does not verify or store the phone's signature; it trusts the signed-in host's console to have done so (RNG-DOSSIER-v1.2.md section 16 item 4). The server does bind each ticket to the pid and device id it was dealt to, and judges a claim only against that pid's tickets.
8. **Duplication and replay.** Each signed phone message carries a strictly increasing counter; the console keeps the highest per pid and drops anything not newer or older than a day. On the server a claim is identified by a reference the console mints; a repeat returns the first verdict (S 810 to 812), and two copies crossing resolve to the one that landed first (S 893 to 897). A ticket is dealt to one pid and one device id.
9. **Records.** All on the server: `vp_bingo_draws` and `vp_bingo_draw_balls` (every ball with ordinal, number, time and source, voided and withdrawn balls kept with a reason), `vp_bingo_tickets` (every ticket, who held it, when, how many balls were out), `vp_bingo_claims` (every press and its verdict and the host's decision), `vp_bingo_patterns` (every pattern ever saved, deletes kept), plus the end-of-game report. All locked to the service role (migrations 70, 104, 118; `RLS-BASELINE.json`). The tablet holds a copy for the room's display. **Gap:** the record tables cascade-delete with the venue and no retention period is stated (20 October check, fix 5).
10. **No selling.** The phone has no purchase path. The bar sells; the host taps; the server caps the count and voids a correction down. The report carries the night's count and prizes.
11. **Software integrity.** The bingo code is one named, versioned module, VP-DRAW-1.2, two files hashed together in `tools/regulated-manifest.json`; the Worker reports the version and manifest hash on /health and the release gate refuses a change without a version rise (`tools/regulated.py`). Every in-scope page and script was downloaded from the live site on 27 October 2026 and matched the commit byte for byte (EVIDENCE-v1.2.md). **Limit:** the deployed Worker is checked by a 32-bit stamp plus the manifest hash, not a full hash of the script.
12. **Failure behaviour.** Phone: a send that cannot go out is queued and flushed on reconnect; a rejoin is answered with the same tickets; a won screen survives a reconnect; the BINGO button stays locked until the host answers. Console: a reload restores the night including the draw id and the claim references. Server unreachable: the console deals opening hands from the tablet only before the first ball and only after an answered failure or a spent budget (index.html 2012 to 2016), calls balls from its pool after four seconds, and reports each; the server accepts a tablet ball only for a place it itself failed to fill or within 30 seconds of a server ball the room never saw (S 100 to 107), and accepts a tablet claim decision only on a draw with a recorded outage (S 907 to 911). Where the state's switch is off, none of that happens and the room waits. Nothing in these paths can change a ticket the server holds or confirm a claim the server judged a non-win.
13. **Patron data.** The join screen on the same page still collects name and, if the venue enabled them, last name, postcode, email, mobile and a marketing opt-in, and posts them to `/capture` (`play.html` 1444 to 1454). It is a different endpoint and table from the game and has no effect on any ticket or verdict, but it is on the ticket page. Decision for Dean (Submission Requirements 6.17).

Jurisdictional controls in the code: `PAPER_BINGO_STATES` (SA, VIC, TAS; `venueplay-game.js` line 169) decided on the server, so no phone ticket is dealt there (S 659 to 664) and the phone shows "tonight you play on paper"; Queensland is not a paper state, which is why this approval matters.

## 4. The gaps, honestly

1. The phone's claim signature is verified by the console, not the server (item 7).
2. Tickets may be dealt after balls are out, and within a 30-second window a host may post a tablet ball in place of a server ball (20 October 2026 check, clauses 4.2.7 and 4.2.4; RNG-DOSSIER-v1.2.md section 16 item 2). Both are decisions for Dean.
3. The opt-in capture sits on the ticket page (item 13).
4. The record tables cascade-delete with the venue and have no stated retention (item 9).
5. The broadcast channel is public: anyone holding the venue's code can read the `cards` messages. Tickets are not secret (every player can see the board, as on paper); integrity rests on the server's copy and the server's verdict, not on secrecy. The submission should say so rather than leave OLGR to discover it.
6. The phone's display was not looked at on a screen for this version (item 4).
