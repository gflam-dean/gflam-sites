## 1. Create the touring worker (about five minutes)

Save on `touring/manage.html` has been dead since the public tables were locked.
The fix is written, tested and pushed. It needs one Worker created.

**NOTHING IN THIS SECTION GOES IN THE SUPABASE SQL EDITOR.** There is no SQL to
run today. Every step below happens in the Cloudflare dashboard or in a browser.

### In Cloudflare

1. **Workers & Pages -> Create -> Worker.** Name it exactly **`touring-api`**.
2. Delete the sample `worker.js` contents and paste in the whole of
   `touring-backend/worker/DEPLOY-touring-api.js`. **Deploy.**
3. Still in Cloudflare: **Settings -> Variables and Secrets.**

   Add these three as **Secret** (the encrypted kind):

   | Name | Value |
   |---|---|
   | `MANAGE_PASSWORD` | a long password you choose. This replaces the old PIN. |
   | `SUPABASE_URL` | `https://gpoolavkghnxedzrmtmc.supabase.co` |
   | `SUPABASE_SERVICE_KEY` | the **service** key from Supabase, NOT the anon one |

   And this one as a plain **Text** variable:

   | Name | Value |
   |---|---|
   | `SITE_ORIGIN` | `https://www.gflamtouring.com.au` |

   Deploy again after adding them.

### Then tell me

Say "worker is up" and I will check it answers correctly and that every secret
took. I do that from here - there is nothing for you to run.

(If you want to look yourself, open this in a browser tab, not in a SQL editor:
`https://touring-api.dean-tindale.workers.dev/health`
It should show `"ok": true` and an empty `missing` list. If a secret is unset it
names which one, and never its value.)

### The real test

Open `www.gflamtouring.com.au/manage.html`, enter the password you chose, and
press Save on a show. That is the whole thing.

If your Worker's URL is not `https://touring-api.dean-tindale.workers.dev`, tell
me what it is and I will change the one line in manage.html that points at it.

**What changed and why.** The old gate was four digits whose SHA-256 sat in the
page source - ten thousand guesses - and it was cosmetic regardless, because the
writes carried the public Supabase key with or without the PIN. Anyone who opened
dev tools could rewrite the tour listings. Now the password is compared in
constant time against a Cloudflare secret, and the service key never leaves
Cloudflare. Reads stay direct, because the public tour pages read the same tables
and there is nothing there to protect.

One consequence: **a refresh asks for the password again.** That is deliberate.
The password authorises every save and is never written to storage, because
anything kept there can be read by any script that gets into the page.

public key. The tables are locked now but this is a separate door, and if that
bucket allows anonymous writes then anyone can put files in it. Worth checking in
Supabase -> Storage -> tour-images -> Policies. Tell me what it says and I will

leak - it would be somebody filling a bucket, not reading anything.
