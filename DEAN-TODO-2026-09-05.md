## 1. Paste the touring worker (about five minutes)

Save on `touring/manage.html` has been dead since the public tables were locked.
The fix is written, tested and pushed; it needs one Worker created.

**The file to paste:** `touring-backend/worker/DEPLOY-touring-api.js`

1. Cloudflare -> Workers -> **Create** -> name it exactly **`touring-api`**
2. Paste the whole file over the default `worker.js`. Save and deploy.
3. Settings -> Variables. Add three **secrets** (encrypted, not plain text):
   - `MANAGE_PASSWORD` - a long password you choose. This replaces the old PIN.
   - `SUPABASE_URL` - `https://gpoolavkghnxedzrmtmc.supabase.co`
   - `SUPABASE_SERVICE_KEY` - the **service** key, not the anon one
   and one plain variable:
   - `SITE_ORIGIN` - `https://www.gflamtouring.com.au`
4. Check it: `curl -s https://touring-api.dean-tindale.workers.dev/health`
   It should say `"ok": true` with an empty `missing` list. If a secret is
   unset it names which one, and never its value.
5. Open `www.gflamtouring.com.au/manage.html`, enter the password you chose,
   and press Save on a show. That is the whole test.

If the worker URL ends up different from
`https://touring-api.dean-tindale.workers.dev`, tell me and I will change the one
line in manage.html that points at it.

**What changed and why.** The old gate was four digits whose SHA-256 sat in the
page source - ten thousand guesses - and it was cosmetic regardless, because the
writes carried the public Supabase key with or without the PIN. Anyone who opened
dev tools could rewrite the tour listings. Now the password is compared in
constant time against a Cloudflare secret, and the service key never leaves
Cloudflare. Reads stay direct, because the public tour pages read the same tables
and there is nothing there to protect.

One consequence: **a refresh asks for the password again.** That is deliberate.
The password authorises every save and is never written to storage, because
anything kept there can be read by any script that gets into the page.
