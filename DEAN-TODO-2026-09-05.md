# Two things to run, in this order

Both in the browser. Nothing here is a terminal command.

---

## 1. Supabase SQL editor  (do this FIRST)

Open `venueplay-backend/supabase/venueplay-63-screen-reload-pull.sql` and paste
the whole thing. It adds one column and nothing else:

    ALTER TABLE public.vp_venues
      ADD COLUMN IF NOT EXISTS screen_reload_at timestamptz;

Safe to run twice.

## 2. Cloudflare  (after the SQL, not before)

Paste `venueplay-backend/worker/venueplay-game.js` over the **venueplay-game**
Worker. Build stamp `b580c4fd`.

The order matters, though I have made getting it wrong survivable: `/venue` is
what every screen polls to check its venue still exists, and two failed reads put
a full-screen "not linked to an account" card over the venue's advertising. If the
Worker went in first, selecting a column that did not exist yet would have done
that to every venue at once. It now falls back to the old query instead. Still do
the SQL first.

## 3. Then reload each screen once, by hand

The last time. After this the screens can be reloaded from HQ even when their
websocket has died, which is the thing that has been beating us.

---

# Why the resets kept coming back

Every remote reload we had travelled on the Supabase realtime broadcast. That is
the thing that breaks. A screen whose socket drops looks completely healthy - the
advertising is built and timed locally and keeps rotating - and cannot be told to
reload over the socket it just lost. So the fix for a broken channel was being sent
down the broken channel, which is why each reset worked once and then stopped: the
next network blip deafened it again, silently.

The reload is now something the screen **pulls**. It already asks
`GET /venue?code=...` every thirty seconds over ordinary HTTPS - that is the
venue-still-exists check - and that request does not care about websockets,
channels or signing. HQ sets a timestamp; the screen's next poll sees it is newer
than its own page load and reloads itself.

Thirty seconds instead of instant, and it works with a dead socket, a channel that
errored out, and broadcast signing enforced. HQ still fires the broadcast too,
because when it works it is immediate. The poll is the floor under it.

Also fixed today, all on the same theme: those five game channels never recovered
from a dropped socket at all (they handled SUBSCRIBED and nothing else), a screen
deaf for four minutes now reloads itself whatever is on screen, and an abandoned
game no longer recaptures the wall every time you tab to the console.

# Still open, when you want them

- **HQ has no screen-health indicator.** A deaf screen has looked identical to a
  working one this whole time, which is most of why this took so long to find. A
  last-heard-from time per screen would have shown it immediately.
- **Group invoicing** (`vp_group_invoices`) is not built. Only bites when a big
  group signs and hits the card limit.
- **Musical and trivia TV screens** may have the same join-QR overlap I fixed on
  bingo. Needs your eyes on a TV.
- **Reload-recovery on musical and raffle** was built but never live-tested: start
  each, refresh the host mid-game, confirm it comes back.
- **Annual overage** is fixed but wants a Stripe test-mode run before your first
  annual venue exists.
